Did: #19 is still blocked, and "CI compiles every report to a PDF" still waits on someone seeing CI. That left one slot. Reading the runner, I found nothing tied a run to the process driving it. I wrote `tests/test_npie_run_lock.py` first and ran it on main. A second `resume` on a run whose `start` was still hung mid-step ran the whole procedure to `passed` (exit 0), so two processes drove one bench. A `start` SIGKILLed mid-step left `running` with no report, and the next `resume` carried on as if the step hadn't begun. I filed "One process drives a run, and a dead one's run ends on record" (serves Safe anywhere) and closed it in this one step. `Run.claim` takes a non-blocking `flock` on the run dir's `run.lock` (`msvcrt.locking` on Windows) and writes the pid. `npie_run.py` claims on start, confirm and resume and lets go when `main` returns. New `runner.abort_orphaned` aborts a run still `running` that a call could claim, turns the supply off, and lets the report be written. The npie_run and runner docstrings and design.md section 3 say so. `make check`: 282 passed, 9 skipped, 73 s. Before the fix, all 4 new tests failed. I also added #81's Closed line and pointed the read-back goal at #81.
Decided: Abort an orphan rather than resume it. The killed step may have left the supply anywhere, so a record that carries on from it isn't a clean one. That matches how a changed design aborts. `status` doesn't claim and doesn't abort, since it only reads. Keep `run.lock` after release rather than unlink it: unlinking races a second process that opened the old file. The cost is a small pid file in each run dir that the boards repo will commit.
Learned: `flock` locks belong to an open file description, so the same process opening the file twice conflicts with itself. In-process tests call `npie_run.main` again and again, so `main` has to let go explicitly (its `held` list). The Windows path is unverified: no Windows host runs the checks.
